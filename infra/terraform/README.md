# Hudaayah — Backend Infrastructure (Terraform)

Terraform for the Al-Fatihah MVP backend: a single `t3.medium` EC2 instance in a
**public subnet** that runs the whole backend stack (Django/DRF + PostgreSQL) with
`docker compose`. Deployments are driven by GitHub Actions using **GitHub OIDC** —
there are **no long-lived AWS keys and no SSH keys stored in GitHub**.

## Layout (modular)

```
infra/terraform/
├── modules/
│   ├── network/            # VPC, public subnet, IGW, route table
│   ├── security/           # EC2 security group
│   ├── iam_github_oidc/    # GitHub OIDC provider + deploy role (SSM only, no secrets)
│   └── ec2/                # t3.medium instance + instance profile + user-data
└── envs/
    └── production/         # root module that wires the modules together
```

## Deploy model (Docker Compose on the instance)

- The instance bootstraps with Docker + Compose + the SSM agent, clones the repo, and
  runs `docker compose up --build` using `/opt/hudaayah/docker-compose.prod.yml`
  (Django `web` via gunicorn + PostgreSQL `db`), generated by Terraform user-data.
- GitHub Actions authenticates to AWS via **OIDC** and triggers a rollout with AWS SSM
  **`SendCommand`**, which runs `/opt/hudaayah/deploy.sh <ref>` on the box. That script
  does `git fetch/reset`, rebuilds the env file from SSM, and re-runs compose.
- Nothing is built or pushed from GitHub, and no registry is used — the image is built
  on the instance from source.

## How deploys stay secret-free

- The OIDC trust policy is scoped to `repo:<owner>/<repo>:ref:refs/heads/main`, so only
  this repo's `main` can assume the role. No access keys live in GitHub.
- The deploy role's only permission is SSM `SendCommand` to this instance plus reading
  command status — nothing else.
- Application secrets (`DJANGO_SECRET_KEY`, DB creds, QF credentials, Google client IDs)
  are read from **SSM Parameter Store** on the instance at deploy time — never baked into
  an image, committed, or placed in GitHub. See `envs/production/README-SSM.md`.

## Usage

```bash
cd infra/terraform/envs/production
terraform init
terraform plan   # review
terraform apply
```

After `apply`, Terraform outputs the values you set as **GitHub Actions variables**
(Settings → Secrets and variables → Actions → Variables, repo or `production`
environment scope) — these are non-sensitive, so they are variables, not secrets:

| GitHub Actions variable | Terraform output |
|-------------------------|------------------|
| `AWS_REGION`            | `aws_region`     |
| `AWS_ROLE_ARN`          | `deploy_role_arn`|
| `EC2_INSTANCE_ID`       | `ec2_instance_id`|

Populate SSM params (`README-SSM.md`) before the first deploy.

> State: for a real deployment move the backend to S3 + DynamoDB locking. The scaffold
> uses local state so you can `apply` immediately; see `backend.tf`.
